# Документация проекта «DOCUMENT LLC» (PHOTO_MANAGER)

> Документ для защиты проекта. Описывает назначение, архитектуру и ключевые
> компоненты без исходного кода и без конфиденциальных данных
> (ключи, токены, учётные записи в документ не включены).

---

## 1. Назначение

Android-приложение для **полевой работы сюрвейеров и инспекторов складов**.
Основные задачи пользователя:

- съёмка фото и видео осматриваемого товара прямо в приложении;
- автоматическое нанесение штампа (компания, дата/время, опционально GPS) на снимок;
- организация снимков по папкам, просмотр, лёгкое редактирование;
- ведение карточек инспекций (товар, поставщик, дата);
- выгрузка отчётов в облако.

Приложение рассчитано на работу «в поле»: оффлайн-съёмка с последующей
фоновой синхронизацией, бережное отношение к памяти на бюджетных устройствах.

## 3. Архитектура

Проект построен по **Clean Architecture** с тремя слоями и однонаправленным
потоком зависимостей (UI → Domain → Data).

```
┌─────────────────────────────────────────────┐
│                 UI Layer                      │
│   Activity / Fragment / Compose / ViewModel   │
│   состояние через StateFlow (UiState)         │
├─────────────────────────────────────────────┤
│                Domain Layer                   │
│   UseCase / интерфейсы Repository / модели     │
│   (бизнес-логика, не зависит от Android API)  │
├─────────────────────────────────────────────┤
│                 Data Layer                    │
│   Repository Impl / CameraX / DataStore /     │
│   FileProvider / Dropbox / WorkManager        │
└─────────────────────────────────────────────┘
```

**Принципы:**
- UI наблюдает за `StateFlow`/`SharedFlow` ViewModel — реактивное обновление.
- ViewModel вызывает UseCase / Repository, не зная о деталях реализации.
- Domain описывает контракты (`interface`), Data их реализует.
- Тяжёлые операции (I/O, сеть, обработка изображений) — на `Dispatchers.IO`.

## 5. Ключевые подсистемы

### 5.1 Камера и фокусировка
- Реализована на **CameraX** с расширением Camera2 interop.
- Управление фокусом и экспозицией через абстракцию `FocusRepository`:
  tap-to-focus, удержание для блокировки AE/AF, трекинг объекта,
  коррекция экспозиции (EV), макро-режим, подсветка для тёмных сцен.
- Состояния фокуса смоделированы **sealed-классом** `FocusState`
  (`Idle → Metering → Locked / Tracking → Failed`) — конечный автомат,
  что делает поведение предсказуемым и тестируемым.
- Есть две реализации: рабочая на CameraX и заглушка на Camera2
  (точка расширения).
- Жесты: тап (фокус), долгое нажатие (блокировка), pinch-to-zoom.

### 5.2 Настройки камеры (`CameraSettingsManager`)
Хранятся в **DataStore** (ключ-значение). Покрывают:
вспышку/фонарик, разрешение и качество фото/видео, ISO, выдержку,
режим фокуса, стабилизацию (OIS/EIS), компенсацию экспозиции, зум,
соотношение сторон, FPS видео, параметры штампа, UI-предпочтения
(ориентация, размер кнопки, скорость анимаций). Значения валидируются
(например, JPEG-качество ограничено диапазоном 70–100).

### 5.3 Штамп на медиа
- `StampConfig` описывает штамп: текст компании, дата, GPS, позиция (4 угла).
- `StampProcessor` наносит штамп на фото и сохраняет EXIF-метаданные
  (дата, GPS, параметры съёмки).
- `VideoStampProcessor` накладывает оверлей на видео через Media3 Transformer.
- Нанесение выполняется фоново в `PhotoSaveWorker` (WorkManager), чтобы не
  блокировать UI.

### 5.4 Захват медиа (`mediacapture`)
Образцовый пример Clean Architecture внутри модуля:
- **domain**: `MediaType`, `MediaCapture`, контракты `MediaFileManager` /
  `PermissionChecker`, `CaptureMediaUseCase`.
- **data**: `MediaFileManagerImpl` (создание файлов с именем по timestamp,
  выдача безопасного URI через FileProvider), проверка разрешений.
- **presentation**: `MediaCameraViewModel` + sealed `MediaCameraUiState`
  (`Idle → Loading → PermissionRequired → ReadyToLaunch → MediaCaptured /
  Cancelled / Error`).

### 5.5 Файловый менеджер
- Грид с адаптивным числом столбцов, множественный выбор (swipe selection).
- Создание папок, импорт из галереи и системного файлового менеджера
  (с учётом Scoped Storage на Android 10+).
- **Корзина**: удаление переносит файлы в trash-каталог, есть очистка.
- **Шаринг**: одиночные файлы — напрямую, папки — упаковка в ZIP, передача
  через `FileProvider` (без выдачи прямого пути к файлу).
- Оптимизация памяти: загрузка превью через Glide, очистка кэша.

### 5.6 Инспекции
- Модели `Inspector` и `Inspection` (товар, поставщик, дата).
- Списки выводятся через адаптеры; экраны добавления/просмотра инспекции.

### 5.7 Авторизация
- Вход администратора через **Firebase Authentication** (email + пароль,
  с авто-регистрацией при первом входе).
- Рядовой сценарий — вход сотрудника по коду.

## 7. Фоновые задачи (WorkManager)

| Worker | Назначение |
|--------|------------|
| `PhotoSaveWorker` | нанесение штампа и сохранение фото вне UI-потока |

закрытия приложения и переживает перезапуск процесса.

## 8. Безопасность

| Правило | Реализация |
|---------|------------|
| Нет секретов в коде | ключи/токены — в `BuildConfig` / `local.properties`, в репозиторий не коммитятся |
| Нет I/O на главном потоке | все операции БД/файлов/сети на `Dispatchers.IO` |
| Безопасный шаринг | `FileProvider` вместо прямых путей |
| Безопасный доступ к памяти | поддержка Scoped Storage (Android 10+) |
| Обфускация | ProGuard/R8 в release-сборке |
| Минимум разрешений | камера, микрофон, геолокация и хранилище — по необходимости |

> Примечание для защиты: в репозитории присутствует тестовый ключ в ресурсах —
> при доработке его следует вынести в `local.properties` и удалить из VCS.

## 9. Используемые паттерны и решения

- **MVVM + Clean Architecture** — разделение ответственности, тестируемость.
- **Repository** — изоляция источников данных от бизнес-логики.
- **UseCase** — инкапсуляция отдельных операций предметной области.
- **Sealed-классы для состояний** (`FocusState`, `UiState`) — явный и
  безопасный конечный автомат вместо набора булевых флагов.
- **StateFlow/SharedFlow** — реактивный, lifecycle-aware UI.
- **Dependency Injection (Hilt)** — слабая связанность, простая замена
  реализаций (например, заглушка камеры в тестах).
- **Модуляризация** (`feature/camera`) — независимая разработка и тесты.

## 11. Интеграция с Dropbox (подробно)

### 12.1 Назначение
Dropbox используется как **облачное хранилище отчётов**: снятые на складе
фото/видео и сформированные архивы выгружаются в аккаунт компании, чтобы
офис получал материалы инспекции без ручной передачи файлов с устройства.

### 12.2 Используемая библиотека
Официальный **Dropbox Java/Android SDK** (`com.dropbox.core`), клиент
версии 2 (`DbxClientV2`). Работа идёт через HTTP API Dropbox; SDK берёт на
себя авторизацию запросов, повторные попытки на уровне транспорта и разбор
ошибок.

### 12.3 Компоненты и их роли

| Компонент | Слой | Ответственность |
|-----------|------|-----------------|
| `DropboxClientFactory` | utils | Создаёт и хранит единственный экземпляр `DbxClientV2` (паттерн Singleton); инициализируется токеном доступа |
| `DropboxRepository` | data | Операции с файлами: список папки, создание папки, загрузка, скачивание; всё на `Dispatchers.IO`, результат в `Result<T>` |
| `DropboxUploadWorker` | workers | Фоновая, гарантированная выгрузка одного файла через WorkManager |

### 12.4 Поток выгрузки

```
Снимок сохранён локально
        │
        ▼
Постановка задачи в WorkManager  (путь к файлу + путь в Dropbox)
        │
        ▼
DropboxUploadWorker.doWork()
        │
        ├─ проверка ограничений фона (Doze / battery optimization)
        │       └─ если запрещено → Result.retry()  (повтор позже)
        │
        ├─ проверка существования файла
        │       └─ нет файла → Result.failure()
        │
        ├─ при необходимости → foreground-уведомление (защита от kill на MIUI/EMUI)
        │
        ├─ получение клиента из DropboxClientFactory
        ├─ upload потоком (WriteMode.OVERWRITE)
        │
        ├─ успех                → Result.success()
        ├─ DbxException (сеть)  → Result.retry()
        └─ прочая ошибка        → Result.failure()
```

### 12.5 Почему WorkManager, а не прямой вызов
- **Гарантия выполнения**: задача переживёт закрытие приложения и
  перезапуск процесса/устройства.
- **Оффлайн-сценарий**: съёмка в поле без сети, выгрузка — когда сеть появится.
- **Устойчивость к OEM-ограничениям**: на MIUI/EMUI агрессивно убивают фон;
  worker распознаёт Doze/battery restriction и переносит попытку (`retry`),
  а при активной выгрузке поднимает foreground-уведомление.
- **Чистая обработка ошибок**: разделение «повторить» (`retry`, сетевые сбои)
  и «провал» (`failure`, нет файла) — без падений UI.

### 12.6 Архитектурная роль
- `DropboxRepository` — реализация контракта работы с облаком, скрывает SDK
  от остального кода (соответствует слою Data в Clean Architecture).
- Все операции возвращают `Result<T>` — вызывающий код не ловит исключения
  SDK напрямую, ошибка обрабатывается явно.
- I/O строго на `Dispatchers.IO` — главный поток не блокируется
  (правило NO MAIN THREAD IO).

### 12.7 Безопасность
- Токен/ключ доступа к Dropbox **не должен** храниться в исходниках —
  место хранения: `local.properties` → `BuildConfig`.
- `DropboxClientFactory` инициализируется токеном на старте, а не хранит
  его в коде.
- Передаются только файлы инспекции; персональные данные в облако не пишутся.
